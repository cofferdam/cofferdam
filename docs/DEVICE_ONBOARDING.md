# Device onboarding and connection states

How a phone or tablet gets a token, what it does with it, and what the user sees when any of
that fails. Written after a real fresh-device failure on iOS Safari, which is documented at the
bottom because the shape of the bug explains most of the design.

---

## How a device authenticates

There is one credential: the **device token**, generated by the service and read from
`$COFFERDAM_HOME/secrets/token` (mode 0600). It is never in git, never in the systemd unit, and
never printed by the PWA.

A device is onboarded by the user typing that token into the **Connect** panel:

1. the field is `type="password"`, so it is masked and stays out of autofill and screenshots;
2. the token is validated against `GET /api/status` **before** it is stored — a typo never
   becomes a persisted setting;
3. only on success is it written to `localStorage` under `cofferdam.token`;
4. **Forget this device** clears it, and re-entering a different token replaces it.

The token is sent two ways, and neither is a URL:

| Channel | Carried in |
|---|---|
| REST (`/api/…`) | `Authorization: Bearer` header |
| Events (`/ws`) | `Sec-WebSocket-Protocol` subprotocol pair, `cofferdam-token` then the token |

The WebSocket subprotocol exists because **browsers cannot set headers on a WebSocket**. The
alternative is a query parameter, and a token in a WebSocket URL reaches browser history, proxy
logs and crash reports. The server accepts a `?token=` fallback for non-browser clients, and the
PWA never uses it.

Server-side authentication is unchanged by any of this. `/ws` is closed with **4401 before the
upgrade** when the token does not match, so an unauthenticated socket is never accepted, and the
REST API answers 401. Nothing in the client is permitted to relax either.

## Connection states

The header shows one of five states. They are exhaustive and every one of them is bounded — an
attempt that goes nowhere has to say so rather than sit spinning.

| State | Header | Means | User's next move |
|---|---|---|---|
| `connecting` | connecting… | first attempt in flight | wait — bounded, see below |
| `auth_required` | not connected | no token on this device | enter the token |
| `auth_rejected` | token rejected | service refused it (401, or ws close 4401) | enter a valid token |
| `unreachable` | unreachable | no answer in time, or the socket died | **Retry** |
| `connected` | live | authenticated, events flowing | — |

Two bounds enforce this:

* `BOOTSTRAP_TIMEOUT_MS` (8s) on the initial `/api/status`, so a black-holed route reports
  unreachable instead of hanging;
* `SOCKET_OPEN_TIMEOUT_MS` (10s) on the WebSocket open, because on iOS a socket to an
  unreachable peer may never fire `onerror` at all.

Only the **first** connection attempt may display `connecting…`. Background reconnects keep the
`unreachable` state visible while they retry underneath — resetting to an optimistic state on
every retry reproduces an indefinite "connecting…" by loop rather than by exception, which is a
bug this project has now had once.

`auth_rejected` deliberately does not retry. A 4401 is a permanent answer about the credential,
and retrying it forever would be persistence dressed over a decision.

## Storage may be refused, and that is survivable

On iOS Safari, `localStorage` **throws on access** — not returns null — under Private Browsing,
"Block All Cookies", and some lockdown/MDM configurations. Every access in `web/app.js` is
therefore wrapped, and when storage is unusable the token is kept in memory for the session.

The device is fully usable in that state. It simply cannot remember, so the panel says so
instead of silently forgetting at next launch.

## The failure this was written for (2026-08-05)

An already-onboarded tablet worked. A fresh iPhone loaded the PWA shell and stayed on
**"Connecting…"** indefinitely — no token form, no error, no way forward.

**Root cause.** `web/app.js` began its boot with a bare `localStorage.getItem(...)` as the very
first statement. On that iPhone the access threw. Nothing caught it, so the exception escaped the
module's IIFE and the rest of the script never ran. `#setup` and `#app` both keep `hidden` in the
served markup and `#connText` ships the literal `connecting…`, so the page was displaying its own
initial HTML. It was not connecting; it was never going to do anything at all.

**Why only the phone.** The tablet had been onboarded earlier and had working storage, so it
never reached the throwing path. The asymmetry was the browser's storage policy, not the network,
the token, the origin, or the WebSocket — none of which were ever reached.

**What was ruled out, and how.**

| Suspected cause | Verdict | Evidence |
|---|---|---|
| stale service-worker assets | ruled out | `web/sw.js` is network-only; it has no `respondWith` and caches nothing |
| WebSocket origin validation | ruled out | the `/ws` endpoint performs no `Origin` check |
| mixed `ws`/`wss` construction | ruled out | scheme is derived from `location.protocol`; the page is served over `http:` and builds `ws:` |
| invalid or missing token on the socket | ruled out | the journal records **no** `/ws` handshake from any address but the tablet's; the phone never reached `connect()` |
| syntax or missing-element error | ruled out | both scripts parse, and every `getElementById` id used at load exists in `index.html` |

**One observation left unattributed.** The journal shows bursts of uvicorn
`WARNING: Invalid HTTP request received.` with no peer address, clustered around the failed
attempt. That is the shape of non-HTTP bytes arriving on a plaintext port — consistent with
Safari's automatic HTTPS upgrade probing `https://` against an `http`-only origin before falling
back. It is **not** the cause of this bug (the shell did load, over HTTP), and it is recorded
here rather than guessed at. Note also that the service runs with `access_log=False`, so
plain HTTP requests are not logged at all; HTTP-level diagnosis is deliberately blind here, and
that is a privacy choice, not an oversight.

**The general lesson, which outlives the specific cause.** A page that ships a hopeful string in
its markup and relies on JavaScript to replace it will display that string forever if the script
dies. The fix is not only the `try`/`catch` around storage — it is that every path now terminates
in an explicit state, the boot is wrapped, and a last-resort `error` listener converts any
unhandled throw into `unreachable` with a Retry. Whatever breaks next, the page says something
true about it.
